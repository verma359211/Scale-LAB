# Three-instance capacity check: 1,100 versus 1,200 RPS

## Summary

Both requested rates are sustainable for two minutes with zero dropped iterations and zero client-visible errors. 1,100 RPS is clean. At 1,200 RPS, latency grows disproportionately and Nginx records three one-second upstream connection timeouts, but its retries succeed and no API instance is temporarily disabled. The system therefore does not break at 1,200 RPS; this point is an early warning region rather than the capacity boundary.

## Environment

- Date: 2026-10-03
- Git commit: `be2cd4044110253834d702a87786cc97493c648b`
- Working tree: dirty because the current observability and experiment work is not committed
- Node.js: v26.3.0
- Runtime: three compiled `node dist/server.js` application imports through `scripts/start-api-instance.mjs`
- `NODE_ENV`: production
- API instances: `api-1:3101`, `api-2:3102`, `api-3:3103`
- Pool maximum: 20 per API, 60 possible application connections in aggregate
- Public endpoint: Nginx on port 3001
- Database: PostgreSQL 16 on port 5433
- k6 executor: `constant-arrival-rate`
- Duration: two minutes per measured point
- Iteration: exactly one `GET /api/products/:id`
- Preallocated VUs: 500
- Configured maximum VUs: 3,000
- Successful API and Nginx access logging: disabled
- Prometheus scrape interval: three seconds

A 15-second 300-RPS warm-up was excluded from measurements. The system then settled for ten seconds before 1,100 RPS. After that run, it settled for another 15 seconds and every API, PostgreSQL and Nginx health check passed before 1,200 RPS began.

|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,100 | 1,100.05 RPS | 132,001 | 0 | 0% | 8.18 ms | 4.97 ms | 10.86 ms | 18.16 ms | 78.41 ms | 532.25 ms | 35 |
| 1,200 | 1,200.05 RPS | 144,002 | 0 | 0% | 10.92 ms | 5.41 ms | 13.38 ms | 25.01 ms | 135.13 ms | 1,010.44 ms | 281 |

The configured arrival rate was achieved at both points. k6 needed at most 35 active VUs at 1,100 and 281 during the brief 1,200-RPS timeout burst. It had 500 VUs preallocated and a configured ceiling of 3,000, so the generator was not the limiting resource.

For only a 9.1% increase in offered load, 1,200 RPS increased average latency by 33.6%, p95 by 37.7%, p99 by 72.3%, and maximum latency by about 90%. This is the strongest indication that 1,200 is entering a tail-latency warning region even though it remains sustainable.

## PostgreSQL pool and query path

| Target | Pool waiters steady avg / max | Acquire rolling p95 steady avg | Acquire rolling p99 steady avg range | Query rolling p95 steady avg range | Query rolling p99 steady avg range | PostgreSQL CPU avg / max |
|---:|---:|---:|---:|---:|---:|---:|
| 1,100 | api-1 0/0; api-2 0.37/11; api-3 0/0 | 0.95–0.95 ms | 0.99–3.80 ms | 6.19–6.82 ms | 15.77–18.93 ms | 69.98% / 113.85% |
| 1,200 | all 0/0 | 0.96–0.97 ms | 4.58–51.54 ms | 9.20–11.30 ms | 27.38–36.52 ms | 73.85% / 137.30% |

The three-second waiter gauge does not show a sustained queue at 1,200, and pool-acquisition p95 remains around one millisecond. However, the rolling acquisition p99 becomes bursty, especially on api-2 where its steady-window average is 51.54 ms and its maximum rolling value reaches 200.98 ms. A short burst can appear in histogram tails without being caught by the three-second instantaneous waiter gauge.

Query p95 and p99 both rise at 1,200, but remain in the tens of milliseconds. PostgreSQL uses more than one CPU core briefly, yet is not at a sustained CPU ceiling. The database path is showing increased tail pressure, not the multi-second pool queue observed during the previous 2,000-RPS collapse.

There are no pool-acquisition timeouts, query errors, HTTP 5xx responses, or client aborts at either point.

## Nginx behavior

| Target | Nginx steady RPS | Active connections | Writing steady avg / max | Keep-alive waiting steady avg | CPU avg / max | Upstream timeouts | Temporarily disabled | No live upstreams |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,100 | 1,100.90 | 501 | 7.47 / 17 | 493.53 | 60.46% / 93.39% | 0 | 0 | 0 |
| 1,200 | 1,196.48 | 501 | 14.23 / 112 | 486.70 | 70.41% / 98.03% | 3 | 0 | 0 |

The 501 active Nginx connections are not 501 queued requests. k6 preallocates 500 workers and reuses keep-alive connections; Nginx classifies most of those idle reusable connections as `waiting`. The `writing` state better reflects connections actively returning responses.

At 1,200 RPS, Nginx recorded these exact events:

- 13:52:25.721 UTC: connection to api-3 on port 3103 timed out for product 3
- 13:52:25.755 UTC: connection to api-3 on port 3103 timed out for product 2
- 13:52:43.295 UTC: connection to api-2 on port 3102 timed out for product 2

The one-second `proxy_connect_timeout` explains the 1.01-second maximum k6 latency. Nginx retried another upstream, so every request still returned successfully. Api-3 received two failures within the ten-second failure window and api-2 received one; neither reached the configured three failures needed for temporary exclusion. Consequently, there were no `temporarily disabled` or `no live upstreams` events.

At the nearest three-second samples to those events, every instance still completed about 400 RPS, Node CPU was only 43–49%, active requests were 1–2 per instance, and pool waiters were zero. This does not match sustained Node, event-loop, or pool exhaustion. The evidence points to transient upstream connection establishment pressure across the Docker Desktop container-to-Windows-host boundary or a short listener/backlog burst. It is not yet frequent enough to reduce throughput.

## Observability health

- All API scrape targets remained `up = 1`.
- The Nginx exporter and its Prometheus target remained `up = 1`.
- Steady API scrape-duration averages were 12.69–22.86 ms at 1,100 RPS and 13.90–21.05 ms at 1,200 RPS.
- Prometheus collected the full three-second series for both test windows.

## Capacity conclusion

### Healthy point

1,100 RPS is clearly healthy: full achieved rate, no drops/errors, even balancing, no Nginx failures, no sustained pool wait and low latency.

### Warning point

1,200 RPS is still sustainable, but it is the first observed warning point. Tail latency increases faster than throughput, query/acquisition tails rise, Nginx writing connections spike, and three upstream connections exceed the one-second connection timeout.

### Break point

The application does **not** break at either requested rate. Combined with the prior experiment, the currently measured boundary is:

```text
1,100 RPS: healthy
1,200 RPS: sustainable with early warnings
unknown region: >1,200 and <2,000 RPS
2,000 RPS: severe overload and Nginx ejection cascade
```

The next controlled sweep should use 1,300, 1,400, 1,500 and then smaller increments around the first point that shows sustained pool waiting, repeated Nginx ejection, dropped iterations, or reduced achieved throughput. No configuration should change between those tests.
