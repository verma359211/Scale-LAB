# Multi-instance capacity check: 1,000 versus 2,000 RPS

## Summary headline

Three API instances are healthy at 1,000 RPS, but 2,000 offered RPS creates database-pool queues, slows PostgreSQL work, and triggers Nginx upstream ejection that converts overload into a 51% HTTP failure rate.

## Environment

- Date: 2026-10-03
- Git commit: `be2cd4044110253834d702a87786cc97493c648b`
- Working tree: dirty; the manifest records this explicitly
- Node.js: v26.3.0
- Runtime: three compiled Node processes
- API instances: `api-1:3101`, `api-2:3102`, `api-3:3103`
- Nginx: Docker container on public port 3001, round-robin upstreams
- PostgreSQL: PostgreSQL 16 container on port 5433
- Pool maximum: 20 per API instance, 60 aggregate
- Workload: k6 `constant-arrival-rate`, one `GET /api/products/:id` per iteration, no sleep
- Duration: two minutes per measured rate
- k6 capacity: 500 preallocated VUs, 3,000 maximum VUs
- Metrics: Prometheus scrape every three seconds; dashboard calculations use 30-second rolling windows

The per-instance averages below use a steady metric window that excludes the first 30 seconds needed to fill rolling PromQL windows and the final five seconds where k6 is stopping. k6 result values cover its complete two-minute execution.

## Failure mechanism

The exact 2,000-RPS window contained:

- 4,060 Nginx `upstream timed out while connecting to upstream` events
- 8,016 Nginx `upstream server temporarily disabled` events
- 110,814 Nginx `no live upstreams` events

The `no live upstreams` count exactly equals k6's 110,814 failed checks. Nginx's one-second upstream connect timeout and `max_fails=3` policy temporarily eject busy Node instances. Once every upstream is considered unavailable, Nginx immediately returns a gateway failure. This explains both the fast failed responses and the severely uneven traffic distribution.

The causal sequence supported by the metrics is:

```text
2,000 offered RPS
  -> PostgreSQL query latency rises
  -> all per-instance pools fill
  -> hundreds/thousands of requests wait for pool clients
  -> in-flight requests and upstream connection pressure grow
  -> Nginx connection attempts exceed one second
  -> Nginx temporarily ejects upstreams
  -> all upstreams can be unavailable simultaneously
  -> Nginx returns 110,814 failures
```

## Bottleneck conclusion

The primary bottleneck is the shared database access path expressed as PostgreSQL pool saturation and rising query execution time. Node CPU, event-loop lag and memory do not show saturation. PostgreSQL uses more CPU but does not exhaust the Docker CPU allocation; further database analysis is required before attributing the query slowdown to a specific PostgreSQL internal resource.

Nginx's upstream-failure policy is a major overload amplifier. It is not the initial bottleneck, but its one-second connect timeout and temporary-ejection behavior turn a slow queued system into a 51% failure event and create oscillating, uneven distribution.

The 3,000-VU ceiling was reached because latency and queued work grew into seconds. Since server-side pool queues, query latency, Nginx timeout events and failed upstream selection all rose concurrently, this is not merely a k6 generator limitation. Increasing max VUs would submit more work to an already overloaded system and would not make 2,000 RPS sustainable.

## Benchmark route correction

An initial attempt used `host.docker.internal:3001` from the k6 container and received immediate connection refusals from Docker Desktop's host-port hairpin. It was interrupted, saved, marked `valid: false`, and excluded from every result above. The valid runs use `http://nginx:80` on the Compose network, preserving the complete k6 -> Nginx -> API -> PostgreSQL path without leaving and re-entering Docker.

## Recommended next experiment

Do not tune pool size, Nginx timeouts or application code from only these two endpoints. Run a constant-arrival-rate sweep at 1,200, 1,400, 1,600 and 1,800 RPS with the same configuration. This will identify where pool waiting and Nginx upstream ejection begin. After locating that knee, run one controlled Nginx-policy A/B at the first failing rate; keep application and pool settings constant and change only upstream failure/ejection behavior. This distinguishes the underlying database-path capacity from the proxy's failure amplification.
